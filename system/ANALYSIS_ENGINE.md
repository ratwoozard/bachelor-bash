# ANALYSIS ENGINE

## Formål

Sikre stringent analyse i `report/04-analysis.md` ud fra **jeres** PF i `PROJECT.md`.

Målet er ikke generel AI-, branche- eller metodeessayistik. Målet er:

- korrekt teoribrug (kun `system/THEORY_REGISTRY.md`)
- evidenskæde
- casekobling inden for `PROJECT.md`-scope
- fortolkning frem for deskription
- Harvard author-year
- ingen opfundne data eller kilder

## Aktiv front

Skriv det kapitel, brugeren peger på. Standard analysefront er `report/04-analysis.md`.

Kapitel 4 må ikke blive metodekapitel, videnskabsteori-dump eller bred organisationsanalyse uden empirianker.

## Method contract

Følg designet i `PROJECT.md` og `report/02-method.md`.

Hvis I kombinerer QUAL og QUANT (Rossman & Wilson, 1984):

1. Kvalitative kilder forklarer praksis, betydning og mulige årsager.
2. Kvantitative kilder viser mønstre, volumen og indikatorer.
3. Triangulering sammenholder — den beviser ikke kausalitet.

Bland ikke datatyper uden eksplicit overgang.

Hvis I bruger KPI/KQI: KPI = procesindikator; KQI = vurderingsdimension. Hurtigere er ikke automatisk bedre.

## Autoritetsrækkefølge (kap. 4)

1. `PROJECT.md`
2. `system/*`
3. `prompts/*`
4. `report/04-analysis.md`
5. `context/evidence/*`
6. `report/STATUS.md`

## Konfliktregel

`system/*` vinder over ældre skriveguides ved kapitel 4.

- `THEORY_REGISTRY.md` vinder for teoribrug.
- `EVIDENCE_CHAIN_RULES.md` vinder for evidenskrav.
- `ANALYSIS_QUALITY_GATES.md` vinder for færdigmarkering.
- `STATUS.md` er dashboard, ikke kilde.

## Dagligt workflow

1. Læs `PROJECT.md` og `report/STATUS.md`.
2. Tjek `EMPIRI_STATUS.md` før tal og citater.
3. Skriv med evidenskæden.
4. Validér mod quality gates.
5. Opdatér STATUS.

## Forbudt

- Opfinde interviews, tal, sidetal eller referencer.
- Antage Lean, DSS, TOE eller andre domænemodeller, medmindre de står i `THEORY_REGISTRY.md`.
- Skrive "beviser" / "forbedrer" uden dokumenteret effekt.
